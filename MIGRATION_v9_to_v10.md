# Migrating from SDK 9 to 10

SDK 10 targets AdCP 3.3. SDK 9 stays on AdCP 3.2 and keeps releasing from
`main`; SDK 10 pre-releases come from `next` (`pip install --pre adcp`). Review
the changes below before upgrading each client, server and reporting worker.
The protocol-side rules are in the AdCP
[3.2 to 3.3 migration guide](https://docs.adcontextprotocol.org/docs/reference/migration/3-2-to-3-3);
the SDK-relevant inventory is [docs/adcp-3.3-sdk-inventory.md](docs/adcp-3.3-sdk-inventory.md).

| Change | Update your integration |
| --- | --- |
| The wire pin is AdCP `3.3.0-beta.0` | `get_adcp_version()` returns `3.3.0-beta.0`; the SDK speaks `adcp_version: "3.3-beta.0"` by default and advertises `3.0`, `3.1`, `3.2`, `3.3-beta.0` and the `3.2-rc.7` alias. A stable `"3.3"` is not an accepted pin until the protocol's 3.3 GA. Pin `adcp_version="3.2"` on a client or server that must keep a 3.2 contract. Generated types, bundled schemas and the versioned validators follow the 3.3 bundle. |
| A server that restricts `supported_versions` pins to its newest listed release | A `PlatformHandler` or `create_adcp_server_from_platform(...)` with `supported_versions=["3.2"]` and no `adcp_version` serves 3.2, instead of raising because the SDK default is outside the list. Pass `adcp_version` explicitly to choose another listed release. |
| `server_version` pins keep wire precision | `ADCPClient(server_version=...)` and `get_server_version()` keep a 3.x pin at release precision: `"3.1.0-beta.1"` reads back as `"3.1-beta.1"` (SDK 9 reported the bundle key, `"3.1.0-beta.1"`). Stable pins still collapse (`"3.0.7"` → `"3.0"`). |
| Translation covers the 3.3 line | Handlers receive requests upgraded to `3.3-beta.0`; `resolve_requested_adcp_version(params)` returns that inside a handler. Read a buyer's negotiated version from `ToolContext.resolved_adcp_version`. Responses to 3.2, 3.1 and 3.0 buyers are converted down; a downgrade the older schema refuses fails as `ADCPVersionConversionError` instead of reaching the peer invalid. |
| `UniversalMacro` is a union | AdCP 3.3 adds the parameterized `GDPR_CONSENT_<gvl_id>` family, so `adcp.types.UniversalMacro` is now a `RootModel` over the closed enum (`UniversalMacro3`) and the pattern string (`UniversalMacro4`). Replace `UniversalMacro.MEDIA_BUY_ID` with `UniversalMacro3.MEDIA_BUY_ID` (or compare strings), and read `.root` on a parsed value. |
| The experimental identity preview is the generated 3.3 surface | `adcp.types.experimental_identity` keeps every name (`AgentOnboarding`, `BuyerOnboardingPosture`, `PrincipalRelationship`, `TrustRecord`, `GetPrincipalResponse`, ...) but binds the generated 3.3 types. `adcp.types._identity_preview`, `adcp.signing._identity_schemas` and `scripts/generate_identity_preview.py` are gone. `RequestSigning.profiles` is `list[Profile]` (an enum) rather than `list[str]`; `PrincipalChangedWebhook.reason` is the generated `Reason` enum, which now includes `relationship_changed` and `relationship_expiring`. `AgentOnboardingRequirement.kind` stays open (`AgentOnboardingRequirementKind | str`). `adcp.signing.validate_identity_value` validates against the pinned bundle; `identity_schema_bundle()` is removed. |
| `reporting_webhook.operation_id` is a generated field | The field, its constraints and its never-null marker come from the 3.3 schema. The SDK 9 runtime patch is gone; nothing changes on the wire. |
| RFC 9421 signing warns by default | AdCP 3.3 deprecates the `adcp/request-signing/v1` and `adcp/webhook-signing/v1` profiles for Web Bot Auth. Constructing `SigningConfig` or `RequestSignatureVerification` without Web Bot Auth emits a `DeprecationWarning`; both profiles keep working through 3.x. |
| `evaluator_id` is gone from evaluator specs | AdCP 3.3 removes the experimental `build_creative.evaluator.evaluator_id` source form. Use inline `exemplars` or `agent_url`; put the seller's evaluator in `creative_policy.accepted_verifiers[]`. |
| Schema defaults appear in dumps for new 3.3 fields | `GetProductsRequest.include_collections` (`false`) and `proposal_refinement.hold_extension` (`false`) carry schema defaults, so a dumped model declares them. Tests that compare whole dictionaries need the new keys; a 3.3 → 3.2 downgrade drops them with a recorded loss. |
| Delivery rows may omit `impressions` | Every `by_*` delivery-metrics row makes `impressions` optional. Treat absence as "not measured", never as zero. |
| Pixel trackers for AdCP 3.3 playback events are dropped when downgraded to the v1 url-tracker shape | `downgrade_pixel_tracker` returns `PixelTrackerDowngrade(v1=None, ...)` with a `PIXEL_TRACKER_LOSSY_DOWNGRADE` advisory for `start`, `first_quartile`, `midpoint`, `third_quartile` and `complete`, and for their 3.2 interim form (`event: custom` with `custom_event_name` set to one of them). SDK 9 put the interim form in the `impression_tracker` slot, which counted every impression as a quartile view. Check `result.v1 is not None` before reading it. `downgrade_pixel_trackers` leaves dropped trackers out of `items`. See the AdCP [3.2 to 3.3 migration guide](https://docs.adcontextprotocol.org/docs/reference/migration/3-2-to-3-3#hosted-video-and-audio-playback-trackers). |
| brand.json fetches accept up to 2 MiB, and refuse a larger configured cap | The default brand.json cap rises from 256 KiB to 2 MiB, as AdCP 3.3 requires. `BrandJsonJwksResolver` and the other brand.json fetchers raise `ValueError` when `max_body_bytes` is above 2 MiB or not positive. Remove a larger override. Documents nested deeper than 32 are refused as `request_signature_brand_json_malformed`, and a fetch has a 10 s total deadline. JWKS and capabilities caps are unchanged. |
| `WebhookReceiver` bounds the body before verifying it | The default body cap falls from 10 MiB to 1 MiB, the AdCP webhook delivery limit. Set `WebhookReceiverConfig.max_body_bytes` per endpoint if you need more. Over-limit bodies, and JSON deeper than 64 or with more than 100,000 members, get HTTP 413 before signature verification. New rejection reasons: `body_too_complex` (413), `content_encoding_unsupported` (415) and `body_framing_invalid` (400). Update code that matches on every reason. Use `read_inbound_body` / `check_inbound_body` in your own push receivers. |
| Client responses have JSON depth and member bounds | After the byte cap, a response, SSE event or MCP text payload deeper than 64 or with more than 100,000 members raises `ADCPResponseTooComplexError`, a subclass of `ADCPResponseTooLargeError`. UTF-16/32 JSON bodies are refused. `max_response_bytes=None` turns off these checks along with the byte cap. |
| A2A requests must meet the AdCP 3.3 operation-resolution hardening when request signing is configured | Send one JSON-RPC request per body with no duplicate or case-variant member names, one content member per Part, no FileParts, and exactly one DataPart carrying `skill`. Otherwise the request fails with `request_body_malformed`. A `message.taskId` continuation must come from the principal that created the task and name its original operation: a different principal gets task-not-found, and a different operation gets `INVALID_REQUEST`. |
| `model_dump()` writes wire names | A field the generator aliased because its wire key is not a Python identifier is emitted under the wire key without `by_alias=True`: `$schema` instead of `field_schema`, `pass` instead of `pass_`, `from` instead of `from_`, `media-buy` instead of `media_buy`, `_truncation` instead of `field_truncation`, `2xl` instead of `field_2xl`. Code that reads a dump by the Python name must read the wire name; pass `by_alias=False` to keep the SDK 9 output. Construction accepts both spellings (`validate_by_name` is on). |
| A received `null` is re-emitted; a Python `None` keyword argument is "not supplied" | A property whose schema admits `null` and that arrived as `null` (`model_validate`, `model_validate_json`, nested validation) stays in `model_fields_set` and is written back as `null` by `model_dump()`. Passing `None` as a keyword argument to a constructor, assigning `None` to a field, or passing `None` in `model_copy(update=...)` now leaves the field *unset*: it is omitted from the dump, and `model_dump(exclude_unset=True)` no longer lists it. A `None` inside a dict you validate is a wire `null`. Properties whose schema does not admit `null` are unchanged (`NoExplicitNull` refuses a JSON `null` and never emits one). |
